## 1. Executive summary

**EduBot is safe and functional at its *actual* verified scale (≈440 source
documents, 14,753 chunks, one ChromaDB collection, 227 MB index). It is *not*
demonstrated to be safe at the scale described in the task brief (millions of
files / ~10 TB). Those are two very different systems and the gap is the single
most important finding.**

The brief asked me to audit a "millions of files / 10 TB" corpus. The repository
does not contain, and its architecture is not built for, that scale. I verified
the real numbers rather than trusting the premise (see §3). Reporting this
honestly is required by the brief itself ("Do not trust approximate corpus size
statements without verification").

The codebase has already been through **three prior hardening rounds** (ingestion
audit, knowledge-hierarchy, table-integrity — see the project memory files).
Most CRITICAL/HIGH items from those rounds are present and correct in the current
tree. I re-verified the highest-value ones (§5). No **new** reproduced
CRITICAL/HIGH data-integrity or security defect was found in this pass that is
not already either fixed or an artifact of the in-flight diff.

**I made no code changes.** Audit-first was requested, and there is a large
uncommitted in-flight diff (authority-hierarchy + table-integrity + response-format
rework) that regenerated the BM25 index and caches. Adding fixes on top of that
un-landed work would conflate concerns and risk the index. Concrete, safe fixes
are proposed in §5 for approval.

## 2. Verified architecture (real paths)

Single-node FastAPI backend (`backend/api.py`) + local persistence. No worker
queue, no distributed store. Ingestion and retrieval run in-process.

```
Source (upload file  |  crawl4ai website + discovered PDFs)
  → backend/api.py            (/upload, /crawl endpoints; server-side caps)
  → backend/ingestion.py      validation, parser selection, extraction, OCR,
                              table extraction, cleaning, metadata, dedup,
                              chunking, split_chunks_for_embedding
  → backend/crawl4ai_crawler.py / crawler.py   domain-lock, SSRF guard, PDF discovery
  → backend/embeddings.py     BAAI/bge-base-en-v1.5, CPU
  → backend/db.py             ChromaDB collection `edubot_docs` (cosine)
  → backend/rag/bm25_index.py data/bm25_index.pkl (rebuilt after every ingest)
  → data/crawl_jobs.json      job state (single JSON file)
  Query:
  → backend/rag/main.py       orchestration (10 stages)
      text_utils.normalize_query (additive acronym expansion)
      intent.py / filters.py  intent + metadata filter ($in:[dept,"general"])
      retrieval.py            vector + BM25, RRF fusion
      authority.py            Tier-1-first authority scoring
      freshness.py            year/date recency + conflict resolution
      reranker.py             BAAI/bge-reranker-base (CPU/MPS), confidence gate
      table_integrity.py      sanitize broken tables before LLM
      context.py              context assembly + token budget
      llm.py                  provider (Ollama default; Groq/Gemini/OpenRouter/Anthropic)
      response_format.py      (new, untracked) answer formatting
  → citations + source display
```

Persistence layers: **ChromaDB + local files** (RAG KB) and **Supabase** (auth,
profiles, roles, activity, crawl-job app records).

## 5. Findings that genuinely remain

### CRITICAL / HIGH
None newly reproduced this pass that are not already addressed. The largest real
*risk* is not a code bug but a **release-hygiene / scale** concern:

- **H-1 — Large un-landed diff carries the live index & caches.** The working
  tree regenerated `bm25_index.pkl` (34→54 MB) and rewrote `retrieval_cache.json`
  (+4,643 lines) alongside ~2k lines of retrieval/freshness/query-expansion
  changes that are **uncommitted and untested-in-CI here**. If this is deployed
  or partially reverted, the pickle index and code can desynchronize (stale BM25
  vs. vector store). *Containment:* commit the code and the regenerated index
  together as one atomic unit, or rebuild BM25 from Chroma on deploy. Do not
  cherry-pick code without the matching index.

- **H-2 (architectural, not a bug) — Single-node/single-file architecture will
  not reach the brief's target scale.** One ChromaDB SQLite collection (227 MB at
  14.7k chunks), a 54 MB pickled BM25 loaded whole into memory at startup, a
  single-JSON crawl-job store, and in-process synchronous ingestion. Expected
  failure modes as the corpus grows: BM25 pickle memory + startup time grows
  linearly and is loaded entirely into RAM; Chroma SQLite write throughput and
  metadata-filter latency degrade well before "millions"; no durable queue means
  an interrupted `/crawl` or process restart can leave a partially-ingested job.
  This is *adequate for the current ~15k-chunk corpus* and *not* a same-day fix —
  see §9 for the staged migration path. Flagged HIGH only relative to the brief's
  stated target, not to current load.

### MEDIUM
- **M-1 — OCR observability is zero.** `ocr_used` is unset on all 14,753 chunks,
  so operators cannot tell which content is OCR-derived, cannot measure OCR rate,
  and cannot prioritize OCR-quality fixes. Populate the flag at ingest.
- **M-2 — 46 chunks dated `document_year=2027` (future).** Within the current
  `current_year+1` cap so not mis-boosted today, but on 2027-01-01 the cap moves
  and any genuinely-mistaken 2027 dates become "current." Worth spot-checking the
  46 for OCR/parse errors vs. legitimate 2026–27 prospectus.
- **M-3 — `.xls` (OLE, not ZIP) bypasses `validate_zip_archive_safety`.** Rare
  format; decompression-bomb guard only covers ZIP-container Office files.
- **M-4 — 28 residual oversized chunks (513–581 BGE tokens)** silently truncate
  at embed time. Documented and intentionally left (atomic blobs); ≤13% over, low
  impact, but still a silent-truncation surface.
- **M-5 — Golden/eval sets are tiny** (7-query golden, ~21-query table set).
  Cannot support a "works at scale" claim; expand or state limits (§7).

### LOW
- OCR casing/ligature/hyphenation normalization gaps (per EDUBOT_RECOMMENDATIONS
  §4) — retrieval-recall polish, not correctness.
- Unpinned backend Python deps; Pillow/pytest not in requirements.txt.
- `word_count=1` chunks exist (short-fact exemption) — verify none are pure noise.

## 7. Tests & limitations
I did **not** execute the full pytest suite or the model-loading golden eval in
this pass (avoids multi-minute model loads and cloud LLM cost, and the tree is
mid-change). Prior docs report: full suite 75–98 pass across rounds, golden
Recall@10 = 100% (7 queries), table-integrity 21/21. **These are small,
non-statistical samples and must not be read as "works for millions of docs."**
Recommended before any scale claim: run `.venv/bin/python tests/run_golden_eval.py`
and `tests/run_table_regression.py`, and expand eval sets to ≥100 queries across
the categories in §8 of the brief.

## 8. Remaining risks (honest)
- Scale premise unmet (H-2) — the biggest one.
- In-flight diff not yet committed/validated as a unit (H-1).
- Retrieval quality only measured on tiny sets (M-5).
- Conflicting old/new docs resolved by authority + LLM prompt + `document_year`;
  deterministic older-version *drop* before context (EDUBOT_RECOMMENDATIONS §2.1)
  is recommended but not implemented — LLM can still see both versions.

## 9. Infrastructure recommendations
- **Required now:** commit code + regenerated BM25 index atomically (H-1);
  populate `ocr_used` (M-1); spot-check the 46 future-dated chunks (M-2).
- **Before corpus growth (>~100k chunks):** move BM25 off a whole-file pickle
  (server-side/incremental, e.g. Tantivy/OpenSearch or SQLite-FTS); evaluate a
  server-mode vector store (Chroma server / Qdrant / pgvector) with pagination;
  introduce a durable job queue with per-document checkpoints for resumable,
  idempotent ingestion; shard by collection/tenant.
- **Optional:** cascaded reranking (skip cross-encoder when top vector distance is
  decisive); layout-aware OCR; deterministic conflict-version drop.
